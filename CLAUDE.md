# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Status

Stages 1–6 are scaffolded (workflow files under `.github/workflows/`, agent prompts under `agents/`, label scripts under `scripts/`). Stages 7–8 (post-merge deploy + production review) are in design — this document captures the intended end-state; their implementation is pending.

See [PIPELINE.md](./PIPELINE.md) for the stage-by-stage flow.

## What this repo is

A **template / centralized workflow** that lets multiple downstream GitHub projects share the same Claude-driven issue-to-production pipeline. Consuming repos opt in by referencing the reusable workflows defined here; this repo holds the agent prompts, stage logic, and shared config schema.

This repo is the source of truth for *the workflow itself*. It is not a deliverable application and does not ship runtime code to end users.

## Architecture

### Runtime: GitHub Actions, not local

The orchestrator is a GitHub Actions workflow running on the consuming repo's runner — not a long-running Claude Code session on a developer's machine. The runner has the consuming repo's real toolchain (Node/Python/Docker/services), so agents can build, run tests, and spin up preview environments without depending on a desktop being online.

Agents are invoked via the official `anthropics/claude-code-action` (pinned to `@v1`). Authentication is via `CLAUDE_CODE_OAUTH_TOKEN` generated by `claude setup-token` — **not an Anthropic API key**. The OAuth token uses an existing Claude Code subscription, so consumers don't need a separate API key or its associated billing setup. One workflow run per stage transition.

Each agent prompt lives in `agents/<stage>/prompt.md` and defines the contract (sections to produce, what to read, what to post). The workflow asks `claude-code-action` to read and follow that prompt, then returns its decision via the action's `structured_output` (driven by a JSON schema in `claude_args`). The structured output is what the workflow routes on; the comment Claude posts is the human-readable artifact.

### Distribution: reusable workflows

Downstream repos consume the pipeline via `workflow_call`. A consuming repo's `.github/workflows/claude.yml` references the workflows here and supplies a small config (see "Consuming-repo config" below).

### State, trigger, and audit log

**Issue labels are the canonical state.** Labels were chosen over Project columns as the source of truth because Projects v2 webhook events fire at the org level (not the repo), which would force every consuming repo into an org-level dispatch setup. Labels are repo-native and make per-project rollout trivial.

A GitHub Project board is *intended* to mirror labels and update on every transition, but **this is not yet implemented**. Treat any references to "the Project board" in this doc or README as a deferred design goal until the sync step exists. Until then, labels are the only state surface.

The label vocabulary the workflow owns:

- `claude:work-this` — applied by a human to enroll an issue. This is the pipeline **trigger**.
- `stage:triage` | `stage:plan` | `stage:dev` | `stage:qa` | `stage:deploy-review` | `stage:pr` | `stage:deploy` | `stage:prod-review` | `stage:awaiting-rollback` — current stage (exactly one at a time).
- `bounce:<from>-<to>:<N>` — bounce counter per stage-pair (e.g. `bounce:dev-qa:2`). Workflow halts at N=3.
- `claude:awaiting-approval` — applied by the workflow at human gates (e.g. plan approval, post-bounce-3 intervention, prod review). Human **removes** the label to approve. To reject: apply `claude:rejected`, or `claude:rejected-auto` at Stage 8 when `rollback:auto-available` is set. Either action fires the next workflow run.
- `deploy:auto` | `deploy:manual` | `deploy:none` — deploy mode for this issue. Stage 5 pre-applies `deploy:none` for doc-only diffs; otherwise the human picks one at Stage 6 before merging.
- `rollback:auto-available` — applied by Stage 5 when it has discovered a viable auto-rollback procedure. Gates the availability of `claude:rejected-auto` at Stage 8.

**The issue comment thread is the audit log.** Every state change — stage transition, label flip, bounce, retry, approval gate opened or closed — gets a short auto-written comment from the workflow. If it didn't get a comment, it didn't happen as far as the audit log is concerned. This is an invariant: agents and the workflow itself must post a comment for every state-changing action, even when the action was triggered by a human label toggle.

### Pipeline: linear, eight stages

Each stage is intended to map 1:1 to a column on the consuming repo's GitHub Project board (deferred — see above).

| # | Stage              | Owner                | Exit condition                                                                                  |
|---|--------------------|----------------------|--------------------------------------------------------------------------------------------------|
| 1 | Triage             | Triage agent         | Scope clear, unknowns/assumptions surfaced and resolved by human; oversized work split into phases or dependencies before handing off |
| 2 | Plan               | Plan agent           | Detailed plan covering dev + deploy + test, approved by human. Scope drift bounces back to Triage |
| 3 | Development        | Dev agent            | Branch with commits ready                                                                        |
| 4 | Verification (QA)  | QA agent             | Branch rebased on `main` first; unit tests pass **and** live-env validation passes against the rebased state. Merge conflicts or new failures bounce to Dev |
| 5 | Deployment review  | Deploy agent         | Infra/migration considerations enumerated; pre-applies `deploy:none` for doc-only diffs; writes deploy + rollback procedures and `deploy:auto-available` / `rollback:auto-available` flags into its comment (this comment is the contract Stages 7–8 read) |
| 6 | PR / Human review  | Human                | Human picks `deploy:auto` / `deploy:manual` / `deploy:none` (constrained by Stage 5's findings) and merges. **No auto-merge.** Merge triggers Stage 7 (or jumps to closure for `deploy:none`) |
| 7 | Deploy             | Deploy agent / Human | **Auto:** agent executes Stage 5's deploy procedure on the runner; failure = hard human gate (no bounce, no retry). **Manual:** workflow opens a human gate; the human deploys + verifies and signals complete — tag is written here, Stage 8 is skipped |
| 8 | Production review  | Human                | **Auto-deploy path only.** Human verifies in prod. Approve → tag is written. Reject → bounces to Plan after rollback completes (auto if Stage 5 found a procedure and the human applied `claude:rejected-auto`; otherwise human rolls back manually and signals) |

### Backflow and loop bounding

- **Failures return to the previous stage with a reason**, posted as a comment on the issue. The previous stage's agent picks it up and tries again. The human is *not* pulled in by default — most QA↔Dev bounces should resolve agent-to-agent.
- **Within a single stage execution: up to 3 internal retries** before the agent gives up and bounces back.
- **Bounce counter per stage-pair: stops at 3.** If a ticket has bounced between the same two stages 3 times (e.g. Dev↔QA, or Stage 8 → Plan on repeated prod rejections), the workflow halts and requires human intervention. This is the hard guard against infinite loops. Most bounces are between adjacent stages; Stage 8 → Plan is the deliberate non-adjacent bounce on prod rejection.

### Deploy queue: tag-gated serialization

Main is protected by a `deployed` tag (or equivalent — git moving tag, GitHub Deployments API, or a `production` tracking branch; pick at implementation time). A branch protection rule requires `HEAD == deployed` for any merge into main. This serializes the post-merge phase: while any ticket is in Stages 7–8, no other PR can merge.

- The tag is written when a human signs off in prod: **Stage 8 approval** (auto-deploy path) or **Stage 7 signal-complete** (manual-deploy path). It is **not** written on Stage 7 auto-deploy success — that would let new PRs merge while prod is still being human-verified.
- For `deploy:none` PRs (doc-only), the tag is written immediately on merge — there is nothing to validate.
- **Bootstrap**: if no `deployed` tag exists yet, the check passes. The first ticket through writes the tag.

### Non-pipeline merges: reverse-engineer flow

Any commit reaching `main` that did not come from a pipeline-managed PR (branch matching `claude/issue-*` with linked issue history) is treated as work-in-flight that needs to be regularized. There is no emergency bypass — hotfixes pay the full validation cost.

1. Workflow detects the non-pipeline commit on the `main` push event
2. Reverts the commit on main
3. Creates an issue from the original PR title/description (or commit message for direct pushes) and applies `claude:work-this`
4. Triage agent inspects the diff and produces a reverse-engineered description and Test plan in a single pass. The Plan stage is skipped: the human's act of merging directly is the implicit Plan approval. This is the one explicit exception to the "every Plan PROCEED gates on human approval" rule.
5. Recreates the branch at `claude/issue-<N>-<slug>` with the original code
6. Issue enters at Stage 4 (QA). Normal pipeline from here.

Test plan quality on reverse-engineered work is best-effort — the agent has only the diff to infer from. If QA fails, the Dev agent fixes the code like any other Dev output, which may mutate the human's original implementation.

### Branching

One branch per ticket: `claude/issue-<N>-<slug>`. Created when the ticket enters Dev (stage 3), accumulates commits through QA and Deploy review, becomes the PR at stage 6, persists through Deploy (stage 7) and Production review (stage 8). No per-stage branches.

### Agent ↔ human communication

Every agent posts a **short, relevant comment** to the issue on each transition: what it did, what it found, what the next stage will receive. Bounce reasons and stage transitions all surface in the issue log. The issue's comment thread is the human-readable audit trail — keep it readable, no dumps of raw tool output.

## Consuming-repo config

There is no consuming-repo config file. Agents discover what they need each run by inspecting the repo (package.json scripts, Makefile, pyproject.toml, Dockerfile, K8s manifests, deploy scripts, etc.). The per-issue contracts are written into stage comments: the Plan agent's Test plan section is the contract for QA, and the Deploy review agent's comment is the contract for Stages 7–8 — it records what it will deploy, how to roll back, and whether each can be done automatically. Downstream stages read that comment to know what options to offer the human and what to execute.

If a consumer wants deploy consistency across issues (so each issue's deploy is inferred the same way), they can encode guidance in their own `CLAUDE.md` rather than introducing a config file here. If repo-side discovery becomes too brittle on real-world repos, a static config file (`.claude-pipeline.yml` or similar) is the obvious next step, but the design *does not* require one.

The only repo-side configuration that exists today is the consuming-repo's `claude.yml` workflow (which references this template's reusable workflows), two secrets the pipeline itself needs (`CLAUDE_CODE_OAUTH_TOKEN`, `CLAUDE_PIPELINE_PAT`), and whatever secrets the consumer's deploy needs (registry tokens, kubeconfig, etc.).

## Open design questions

Decide before — or as part of — implementing the relevant stage. Do not silently pick a default.

1. **Permissions**: scope the Action's GitHub token (repo write, project write, deploy creds) before building anything that needs them.
2. **Tag mechanism**: pick between a git moving tag, GitHub Deployments API, or a `production` tracking branch for the `deployed` marker. All three satisfy the design; differ in tooling/visibility/audit.
3. **Non-pipeline merge detection**: precise rule for "this commit is non-pipeline" — branch name (`claude/issue-*`) plus linked issue with prior stage labels is the obvious start, but admin pushes and force-pushes need explicit handling.
4. **Stage 5 procedure format**: how the deploy/rollback procedures are encoded in the Stage 5 comment so Stages 7–8 can reliably execute them (fenced shell block, structured YAML, plain prose re-interpreted by an agent, …).

### Locked-in decisions (do not re-litigate without explicit reason)

- Runtime: GitHub Actions on the consuming repo's runner.
- Agent invocation: `anthropics/claude-code-action@v1` with `--json-schema` for structured output.
- Auth: `CLAUDE_CODE_OAUTH_TOKEN` (generated by `claude setup-token`), not an Anthropic API key.
- Distribution: reusable workflows via `workflow_call`.
- Pipeline shape: linear eight stages, no adversarial layer, no auto-merge, no auto-close of the issue.
- Backflow: failure → previous stage with reason; 3 internal retries per stage; halt after 3 bounces between the same stage-pair. The Stage 8 → Plan bounce (prod rejection) is counted the same way.
- Branching: one branch per ticket (`claude/issue-<N>-<slug>`), persists stages 3–8.
- State of truth: issue labels. Project board is a synced view.
- Trigger: `claude:work-this` label applied to an issue, OR the workflow detects a non-pipeline merge to `main` and auto-creates an enrolled issue (reverse-engineer flow).
- Approval gates: workflow adds `claude:awaiting-approval`; human removes it to approve, or applies `claude:rejected` to bounce.
- Plan approval policy: **every** Plan PROCEED gates on human approval; there is no "fast path" flag. The single exception: reverse-engineered work (from non-pipeline merges) skips the Plan stage entirely — the act of merging directly is the implicit approval.
- Deploy mechanism: agent-discovered, not consumer-configured. Stage 5 inspects the project and writes deploy + rollback procedures into its comment; Stages 7–8 read that comment. No consumer-side workflow file is required for deploy or rollback. If the agent cannot confidently figure deploy out, only `deploy:manual` is offered.
- Deploy mode choice: human applies `deploy:auto` / `deploy:manual` / `deploy:none` at Stage 6 before merging. Stage 5 may pre-apply `deploy:none` for doc-only diffs; otherwise Stage 5's findings constrain which auto/manual options are visible.
- Auto-deploy failure: hard human gate. No bounce, no retry. The 3-bounce rule does not extend to deploy failures (they are usually creds/infra, not code).
- Manual deploy collapses Stages 7+8: when the human deploys themselves, they are also the verifier; one human signal completes both. Stage 8 only exists for the auto-deploy path.
- Deploy serialization: branch protection on `main` requires HEAD to equal the `deployed` tag. The tag is written when a human signs off in prod (Stage 8 approval for auto-deploy, Stage 7 signal-complete for manual), and immediately on merge for `deploy:none` PRs. New PRs cannot merge while a ticket is in Stages 7–8.
- Stage 8 rejection flow: human (or Stage 5's auto-rollback procedure when `claude:rejected-auto` is applied and `rollback:auto-available` is set) rolls back prod. After rollback completes, the pipeline auto-reverts the merge from main, advances the tag to the revert SHA, and bounces the issue to Plan with the rejection reason as context.
- Pre-PR sync check: Stage 4 (QA) rebases the branch on `main` before running tests. Merge conflicts or new failures bounce to Dev. QA always validates the rebased state — what will actually land.
- Issue closure: the human closes the issue manually, after the pipeline reaches its end (Stage 8 approval for auto-deploy, Stage 7 signal-complete for manual, or merge for `deploy:none`). Closure was not moved to auto in any path.
- Chaining auth: stage-to-stage label transitions are performed by a fine-grained PAT (`CLAUDE_PIPELINE_PAT`), not the workflow's default `GITHUB_TOKEN`. GitHub deliberately suppresses workflow runs triggered by `GITHUB_TOKEN`-driven events to prevent recursion, which would silently break the entire chain after Triage.
- PR rejection: closing a PR without merging is a manual operation. The pipeline does not auto-recover; the human re-enrolls the issue (e.g. by applying `claude:work-this` again) if they want another pass.
- Cost visibility: every stage's transition comment ends with `💰 Cost: $X (this run) | $Y (issue total)` and an HTML-comment marker the next stage uses to compute the running total. No hard budget cap — the 3-bounce limit per stage-pair bounds the worst-case spend, and the visible total lets a human notice if a workflow is misbehaving.
- Audit log: every state change emits a short auto-written issue comment.
- Labels are self-healing: `scripts/ensure-labels.sh` runs at the start of every stage workflow and creates missing labels from `config/labels.json`.

## Out of scope — do not drift toward these

- No adversarial layer or multi-agent debate. The pipeline is deliberately linear.
- No auto-merge. The PR always lands in front of a human.
- No auto-close of the issue. The human closes it after the pipeline reaches its end (Stage 8 approval, Stage 7 signal-complete for manual deploys, or merge for `deploy:none` PRs).
- No unbounded retries anywhere.
- No long-running local Claude Code orchestrator. All execution is per-event GHA runs.

## Commands

This repo has no local build/test commands — all execution is in GitHub Actions on a consuming repo's runner. There is nothing to `npm install` or run locally.

The only local command relevant to this repo is one a *user of the template* runs once to generate their auth token:

```
claude setup-token
```

The output goes into a consuming repo's `CLAUDE_CODE_OAUTH_TOKEN` secret. See `README.md` for full setup.
